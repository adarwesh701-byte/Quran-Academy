# خطة اختبار أمني مصرح بها — بيئة Staging فقط

## قواعد السلامة
- لا تنفذ اختبار اختراق على Production أو حسابات طلاب حقيقيين دون تصريح ونطاق مكتوب.
- استخدم مشروع Supabase منفصلًا وبيانات اصطناعية وحسابات اختبار لكل دور.
- لا تستخدم بيانات دفع حقيقية؛ استخدم Sandbox لدى مزود الدفع.
- لا تنفذ DoS أو brute force واسعًا أو حذفًا/تعديلًا جماعيًا.
- احتفظ بسجل وقت الاختبار والطلب والنتيجة، واحذف بيانات الاختبار بعد المراجعة.

## مصفوفة الأدوار المطلوبة
| الدور | يجب أن يستطيع | يجب ألا يستطيع |
|---|---|---|
| زائر | قراءة الصفحات العامة والمحتوى المنشور | قراءة بيانات الحسابات أو المحتوى الخاص |
| طالب A | قراءة وتعديل بياناته المسموح بها وطلباته | قراءة/تعديل ملف طالب B أو درجاته أو طلباته |
| طالب B | نفس صلاحيات الطالب | الوصول إلى بيانات A بتغيير UUID أو ID |
| معلم | إدارة الفصول/الطلاب المسندين إليه فقط وفق نموذج البيانات | ترقية نفسه أو إدارة معلم آخر أو الوصول إلى مالك |
| مدير | مهام الإدارة المحددة صراحة | ترقية مالك أو قراءة أسرار غير لازمة |
| مالك | مهام المالك الموثقة | مشاركة الجلسة أو المفاتيح السرية؛ كل إجراء حساس يجب تسجيله |

## حالات اختبار IDOR وRLS
1. سجل الدخول كطالب A، واطلب سجل طالب B باستخدام UUID معروف لحساب الاختبار.
2. كرر على SELECT وINSERT وUPDATE وDELETE وRPC وStorage.
3. حاول تغيير `role` أو `owner_id` أو `student_id` من العميل.
4. استدعِ RPC مباشرة دون المرور بالواجهة.
5. جرّب جلسة منتهية ورمزًا غير صالح ومستخدمًا غير مصادق.
6. تأكد أن الملفات الخاصة لا تُفتح عبر URL عام أو Signed URL منتهي.
7. تأكد أن نتائج الرفض لا تكشف بيانات حساسة.

## حالات الدفع
- تغيير order_id إلى طلب مستخدم آخر.
- مبلغ أقل/أكبر بقرش واحد، وعملة خاطئة.
- HMAC غير صحيح أو ناقص أو معاد استخدامه.
- Webhook مكرر ومتزامن.
- فشل بعد تحديث الطلب وقبل تفعيل الاشتراك والعكس.
- إلغاء/استرداد/عملية pending أو failed.
- تأكد أن إعادة إرسال طلب Capture لا تمنح اشتراكًا إضافيًا.

## معايير الإغلاق
كل حالة لها: رقم، دور، بيئة، خطوات إعادة الإنتاج، النتيجة المتوقعة، النتيجة الفعلية، دليل، تصنيف خطورة، مالك الإصلاح، واختبار Regression. لا تُغلق مشكلة HIGH/CRITICAL دون إعادة اختبار مستقل.
